# Методика расчётов HR Survey Analytics

Этот документ описывает не план развития, а фактическую логику, реализованную в текущем коде проекта. Источник истины — файлы в `src/`; если формулировка в документе расходится с кодом, действующим считается код.

Методика рассчитана на фиксированную анкету и листы Google Sheets `Ответы 2025` и `Ответы 2026`. Универсального конструктора анкет и автоматического подключения новых лет в проекте нет.

## Как читать отчёт без знания статистики

Отчёт отвечает на пять разных вопросов. Их важно не смешивать.

| Что показано | Простой смысл | Чего это само по себе не доказывает |
|---|---|---|
| Текущий уровень | Как сотрудники оценили тему сейчас | Почему получилась именно такая оценка |
| Изменение к прошлому году | Насколько показатель вырос или снизился | Что изменение обязательно устойчивое, а не случайное |
| Статистическая значимость | Достаточно ли данных, чтобы считать изменение неслучайным | Что изменение крупное и требует немедленного действия |
| Цвет светофора | В какую внутреннюю зону внимания попал результат | Что ситуация объективно хорошая или плохая: цвета основаны на внутренних порогах проекта, а не на данных рынка |
| `n` | Сколько ответов реально участвовало в конкретном расчёте | Что отвечавшие полностью представляют всех сотрудников |

Безопасный порядок чтения такой:

1. Сначала посмотреть `n`: на малой группе результат сильнее меняется от нескольких ответов.
2. Затем посмотреть сам уровень и размер разницы.
3. Проверить, подтверждена ли разница статистически.
4. Сопоставить сигнал с комментариями, другими показателями и рабочим контекстом.
5. Принимать решение не по одной цифре, а по сочетанию масштаба, надёжности и важности темы.

Коротко: **цвет показывает, куда смотреть; значимость — насколько можно доверять отличию; величина изменения — насколько оно практически важно**.

### С какого листа начать

| Лист | На какой вопрос отвечает | Как использовать |
|---|---|---|
| `Выводы` | Какие сигналы система считает главными | Начать чтение здесь, затем проверить детали на остальных листах |
| `Светофор` | Где текущий уровень хороший, а где требуется внимание | Выбрать темы для обсуждения, не считать цвет готовым диагнозом |
| `Драйверы` | Какие темы меняются вместе с лояльностью | Искать возможные направления работы; связь ещё не доказывает причину |
| `Отклонения срезов` | Какие группы отличаются от общего результата | Проверять локальные зоны риска и учитывать размер группы |
| `Когорта` | Как изменились ответы одних и тех же людей | Отделить личную динамику от изменения состава ответивших |
| `Сервисные vs доменные` | Чем сервисные команды отличаются от доменной разработки внутри Управления разработки ПО | Смотреть разрыв 2026 года и годовую динамику каждой группы отдельно, учитывая статус значимости |
| `Руководитель и команда` | Где взгляд руководителя расходится с мнением команды | Использовать как повод для разговора, особенно осторожно при малой команде |

### Мини-словарь

| Термин | Простое объяснение |
|---|---|
| `n` | Число ответов, реально участвовавших в конкретном расчёте |
| Валидный ответ | Ответ, который можно корректно использовать для этой метрики |
| Дельта, `Δ` | Разница между двумя значениями |
| Процентный пункт, п.п. | Прямая разница процентов: рост с 40% до 45% равен 5 п.п. |
| Срез | Отдельная группа сотрудников, например отдел, город или стаж |
| Когорта | Одни и те же люди, найденные в обоих замерах |
| Погрешность | Диапазон, внутри которого результат может колебаться из-за случайного состава ответивших |
| Статистическая значимость | Признак того, что найденную разницу уже трудно объяснить одной случайностью |
| Корреляция | Две оценки часто растут или снижаются вместе; это не доказывает, что одна вызывает другую |
| Драйвер | В этом отчёте — тема, статистически связанная с eNPS, а не доказанная причина eNPS |
| Эвристика | Практическое правило для быстрой навигации, а не строгий статистический вывод |

## 1. Какие аналитические контуры есть в системе

В проекте работают три связанных, но разных контура.

| Контур | Что делает | Основные точки входа |
|---|---|---|
| Обычный отчёт | Строит оформленный отчёт по выбранному году и срезу, при необходимости сравнивает 2026 с 2025 | `buildReport`, `ReportBuilder` |
| Расширенная аналитика | Строит светофор, статистическую динамику, драйверы, срезы, автоматические наблюдения и когорту | `AnalyticsService`, `AnalyticsWriter` |
| Руководитель и команда | Сравнивает личный ответ руководителя со средней оценкой сотрудников его отдела | `ManagerTeamReport` |

Пункт меню **«Расширенная аналитика»** сейчас всегда запускает 2026 против 2025 без пользовательских фильтров. Внутренний метод `AnalyticsService.build()` фильтры поддерживает, но текущий интерфейс их в этот запуск не передаёт.

После запуска расширенной аналитики создаются или обновляются листы:

- `Выводы`;
- `Светофор`;
- `Драйверы`;
- `Отклонения срезов`;
- `Связи срезов`;
- `Когорта`;
- `Сервисные vs доменные`;
- `Руководитель и команда` — только для 2026.

## 2. Общая последовательность расчёта

```text
Исходные листы
    ↓
Загрузка и фильтрация строк
    ↓
Базовая статистика обычного отчёта
    ├─ eNPS
    ├─ средние rating5
    ├─ распределения
    └─ Top-5 множественных ответов
    ↓
Сравнение периодов и построение обычного отчёта

Те же отфильтрованные строки
    ↓
Кодирование ответов в числовые векторы
    ↓
Светофор и проверка значимости
    ↓
Когорта, драйверы, срезы и эффект состава
    ↓
Автоматические наблюдения расширенной аналитики
```

Обычный и расширенный контуры используют одни и те же правила категоризации eNPS из `Scoring.enpsCategory()`. Это не позволяет разным листам считать промоутеров и критиков по разным границам.

## 3. Источники данных и формирование выборки

### 3.1. Основные листы

- `Ответы 2025` — одна строка на анкету 2025 года;
- `Ответы 2026` — одна строка на анкету 2026 года;
- `перформанс` — справочник для обогащения данных 2026 года;
- `Численность` — редактируемый справочник года, стабильного ID отдела, управления, необязательного типа команды, названия отдела и числа приглашённых.

Первая строка листа ответов считается строкой заголовков. Все остальные строки входят в исходную выборку, даже если часть ячеек пуста.

`DataLoader` читает лист целиком через `getValues()` и кэширует результат только на время одного запуска Apps Script. Исходные листы код не изменяет.

### 3.2. Что означает размер выборки

Размер выборки отчёта — количество строк после применения фильтров. Это не означает, что по каждой метрике есть столько же ответов.

У каждой метрики своя база:

- для eNPS — число валидных оценок eNPS;
- для средней rating5 — число валидных оценок 1–5;
- для доли — число валидных ответов на конкретный вопрос;
- для корреляции — число людей, ответивших на оба сравниваемых вопроса;
- для команды — число сотрудников, ответивших именно на рассматриваемый вопрос.

Поэтому рядом с результатом нужно читать `n`, а не только общий размер отчёта.

### 3.3. Фильтры

Фильтры применяются до расчётов.

- Разные вопросы объединяются через **И**: строка должна пройти каждое условие.
- Несколько выбранных значений одного категориального вопроса объединяются через **ИЛИ**.
- Числовые фильтры `rating5` и `eNPS` используют операторы `=`, `>`, `>=`, `<`, `<=`, `!=` и остаются отдельными условиями через И.
- Регистр и повторяющиеся пробелы в текстовых значениях не учитываются.
- Для отдела перед сравнением применяется справочник переименований.
- `Управление` не хранится в анкете: оно вычисляется по отделу через `Headcount`.
- `Группа команд` — тоже не хранится в анкете: вычисляется по отделу через `Headcount.teamGroupOf` как пара «Управление + Тип команды» (см. 3.5). Отдел без заполненного типа команды под этот фильтр не попадает ни при одном значении.

В пакетном режиме каждый фильтр с режимом `split` разворачивается независимо. Например, два города и три отдела дают пять отчётов, а не шесть комбинаций «город × отдел».

### 3.4. Переименования отделов

`DepartmentAliases` приводит известные старые названия к текущему каноническому названию. Это используется в фильтрах, срезах, сравнении состава и справочнике численности.

Текущий реестр содержит три соответствия:

| Старое значение | Каноническое значение |
|---|---|
| Отдел сетевого администрирования | Отдел сетевых технологий |
| Отдел локализации | Отдел локализации и перевода |
| Отдел программируемых микрокотроллеров | Отдел программируемых микроконтроллеров |

Неизвестное название не удаляется и не заменяется: оно остаётся как есть и попадает в предупреждение журнала.

### 3.5. Тип команды и группа команд

Лист `Численность` имеет структуру `Год | ID отдела | Управление | Тип команды | Отдел | Численность`. Колонка `Тип команды` — **необязательное** поле: в ней встречаются значения вроде `Сервисная команда` и `Доменная разработка`, но справочник не ограничен этими двумя — новые значения (например, для ИТ-управления) не требуют изменений в коде, состав всегда читается с листа.

Ключевые правила (реализованы в `Headcount.gs`):

1. Если у отдела за конкретный год указан тип команды, все ответы сотрудников этого отдела за этот год входят в соответствующую группу.
2. Пустое значение — не ошибка: отдел просто не входит ни в одну группу по типу команды, но продолжает участвовать в расчётах компании, управления и отдела. Синтетическая группа вида «Не указано» не создаётся.
3. Принадлежность определяется **отдельно для каждого года** — тип команды не переносится из 2026 в 2025 и обратно. Связывание строк одного отдела между годами идёт через стабильный `ID отдела`, как и для управления/названия.
4. Логическая **группа команд** — это составной ключ `Управление + Тип команды` (`Headcount.teamGroupOf`, разделитель ` → `). Одинаковое название типа команды в разных управлениях — это разные группы: сервисные команды Управления разработки ПО не объединяются с сервисными командами ИТ-управления.
5. При конфликтующих непустых типах команды у одного `ID отдела` за один год побеждает первая встреченная строка (то же правило, что и для конфликта управлений), а расхождение попадает в предупреждения `Headcount.diagnoseHeadcount`, не останавливая расчёт.

Производный фильтр/срез **«Группа команд»** (как и «Управление») не хранится в анкете — он вычисляется по отделу строки. Он поддержан:

- в фильтрах Sidebar (одиночный и пакетный режимы, `mode: "split"`);
- в срезах `Segments`/`AnalyticsService.build` наравне с «Отделом» и «Управлением» — с численностью, явкой, отклонением от нормы компании и годовой динамикой;
- в знаменателе приглашённых `Headcount.invitedForFilters` — фильтры «Управление» + «Группа команд» + «Отдел» пересекаются через **И**.

## 4. Кодирование ответов

Расширенная аналитика переводит каждый шкальный вопрос в числовой вектор. Длина вектора всегда равна числу строк выборки: позиция `i` относится к одному и тому же респонденту во всех вопросах.

| Тип или вопрос | Кодирование |
|---|---|
| `rating5` | число 1–5 |
| `eNPS` | число 0–10 |
| Да / Скорее да / Скорее нет / Нет | 4 / 3 / 2 / 1 |
| Выгорание | Совсем не чувствовал = 5; редко = 4; регулярно = 2; постоянно = 1 |
| Смена работы | Совсем не задумывался = 4; очень редко = 3; время от времени = 2; постоянно = 1 |

Все шкалы направлены одинаково: **чем больше число, тем лучше состояние**. Поэтому низкие баллы выгорания и смены работы означают повышенный риск.

### 4.1. Что становится `null`

В числовой вектор не попадают:

- пустая ячейка;
- `не пользовался`;
- `затрудняюсь ответить`;
- `-` и `—`;
- нераспознанный текст;
- число за пределами допустимой шкалы.

Такие значения становятся `null`, а не нулём. Это принципиально: в JavaScript `Number("")` равно `0`, поэтому пустую ячейку нельзя без проверки передавать в числовой расчёт.

Ответ `затрудняюсь ответить` исключается из числовой шкалы, но для риск-вопросов дополнительно учитывается как отдельная содержательная группа.

## 5. Базовые показатели обычного отчёта

### 5.1. eNPS

Категории задаются один раз в `Scoring.ENPS_THRESHOLDS`:

- 9–10 — промоутеры;
- 7–8 — нейтралы;
- 0–6 — критики.

Формула:

```text
eNPS = доля промоутеров, % − доля критиков, %
```

Пример: 60% промоутеров и 15% критиков дают eNPS `+45`.

В обычном отчёте доли категорий и eNPS округляются до целого. Пустые и невалидные значения в знаменатель не входят.

### 5.2. Средняя оценка rating5

```text
среднее = сумма валидных оценок / число валидных оценок
```

Учитываются только числа от 1 до 5. Пустые значения, `не пользовался`, текст и числа вне шкалы исключаются. Результат округляется до двух знаков.

Дисперсия сохраняется вместе со средним, потому что она нужна для t-критерия Уэлча при сравнении лет.

Показатель «Средняя оценка раздела» в оформленном отчёте — невзвешенное среднее уже рассчитанных средних вопросов этого раздела. Каждый вопрос имеет одинаковый вес, даже если по одному ответили 300 человек, а по другому — 80. Это обзорная величина для навигации, а не единое среднее всех индивидуальных ответов раздела.

### 5.3. Распределение ответов

Для каждого варианта считаются количество и доля от всех валидных ответов на вопрос:

```text
доля варианта = count варианта / сумма count всех вариантов вопроса × 100%
```

Порядок вариантов фиксирован каталогом `Questions` и не зависит от частоты. Для `rating5` порядок — 5, 4, 3, 2, 1, затем `не пользовался`, если такой вариант есть.

В распределении `не пользовался` и `затрудняюсь ответить` показываются как отдельные ответы и входят в знаменатель распределения. Это отличается от числового вектора, где они равны `null`.

### 5.4. Положительная и отрицательная группы

Для обычных шкал «Да / Скорее да / Скорее нет / Нет» отчёт объединяет ответы:

```text
позитив = Да + Скорее да
негатив = Скорее нет + Нет
```

Названия групп зависят от смысла вопроса: например, «Мнение учитывается», «Получают обратную связь», «Понимают цели компании».

Для расширенного светофора отдельно считается жёсткий негатив:

```text
жёсткий негатив = доля ответа с кодом 1
```

### 5.5. Риск выгорания и ухода

Повышенный риск выгорания:

```text
чувствовал регулярно + чувствовал постоянно и чувствую сейчас
```

Повышенный риск ухода:

```text
задумывался время от времени + постоянно и думаю об этом сейчас
```

В коде выбран знаменатель `Norms.RISK_DENOMINATOR = "answered"`:

```text
риск, % = рискованные ответы / ответы по содержательной шкале × 100%
```

`Затрудняюсь ответить` не входит ни в числитель, ни в знаменатель риска. По выгоранию эта группа показывается отдельно и считается от суммы содержательных ответов и затруднившихся.

### 5.6. Охват вопроса

В обычном и расширенном контурах охват получается немного разными путями.

**Обычный отчёт.** Для настроенных rating5-вопросов `ReportBuilder` берёт из готового распределения округлённую долю ответа `не пользовался` и фактически читает охват как `100% − доля не пользовавшихся`. В Top/Bottom Short Summary попадают только показатели с таким охватом не ниже 45%. Вопрос без варианта `не пользовался` считается охваченным на 100%.

**Расширенная аналитика.** `Scoring.coverage()` делит непустые ответы на две группы:

- `covered` — любое непустое значение, которое не входит в закрытый список `notCovered`;
- `notCovered` — `не пользовался`, `затрудняюсь ответить`, `-` или `—`.

Пустые ячейки в знаменатель охвата не входят.

```text
охват = covered / (covered + notCovered) × 100%
```

Пример: 40 человек поставили оценку, 60 выбрали `не пользовался`, ещё 10 пропустили вопрос. Охват равен `40 / (40 + 60) = 40%`; 10 пропусков в знаменатель не входят.

Для офисных сервисов и льгот охват показывает долю людей с опытом использования. Для остальных типов вопросов это технически тот же расчёт, но обычно он менее содержателен.

Сам расчёт охвата не проверяет, распознал ли `Scoring.vector()` значение и попадает ли число в допустимый диапазон. Поэтому опечатка или неизвестный непустой ответ может увеличить `covered`, хотя в числовой метрике превратится в `null`.

### 5.7. Top-5 множественных ответов

В вопросах `Ценишь в компании` и `Зоны роста компании` одна ячейка может содержать несколько выбранных вариантов. Код разделяет их по последовательности `.,`.

Знаменатель — число респондентов с непустым ответом на вопрос, а не сумма всех выборов:

```text
доля варианта = сколько респондентов выбрали вариант / сколько респондентов ответили на вопрос
```

Поэтому сумма долей может быть больше 100%.

При сравнении лет берётся объединение Top-5 обоих лет: вариант не исчезает только потому, что в одном году оказался шестым.

### 5.8. Темы и тональность комментариев

В Short Summary анализируются:

- `Открытая ОС 1`;
- `Открытая ОС 2`;
- свободный текст из полей «свой вариант» в двух множественных вопросах.

Алгоритм словарный, а не модель машинного обучения:

1. Комментарий делится на предложения по точкам и переносам строк.
2. Тема находится по подстрокам из `THEME_DICTIONARY_`.
3. Позитивные и негативные маркеры ищутся только в предложениях, где найдена тема.
4. Один комментарий даёт не больше одного результата на одну тему.
5. Тема выводится, только если встретилась более одного раза во всей выборке.

Тональность бывает `positive`, `negative`, `mixed` или `neutral`. Такой детектор может ошибаться на иронии, отрицаниях, новом словаре и неоднозначных формулировках; его результат — способ быстро найти повторяющиеся темы, а не полноценный качественный анализ текста.

## 6. Сравнение 2026 с 2025

Одни и те же фильтры применяются к каждому году отдельно. После этого сравниваются уже рассчитанные показатели.

### 6.1. Дельты

- eNPS — разница в пунктах;
- средние rating5 — разница в баллах;
- доли вариантов и категорий — разница в процентных пунктах;
- Top-5 — разница долей без теста значимости.

Отсутствие валидных данных обозначается `null`, а не фиктивным нулём.

### 6.2. z-критерий двух долей

Используется для долей ответов, долей категорий eNPS и долей позитива/риска.

```text
p  = (x1 + x2) / (n1 + n2)
SE = √(p × (1 − p) × (1/n1 + 1/n2))
z  = (x1/n1 − x2/n2) / SE
```

В коде разница считается значимой при `|z| > 1,96`; сильной — при `|z| > 2,58`.

Простыми словами: тест сопоставляет размер разницы с обычным разбросом ответов. Чем больше разница и чем больше валидных ответов, тем сложнее объяснить результат случайностью.

### 6.3. t-критерий Уэлча

Используется для независимых средних rating5 двух лет.

```text
SE = √(s1²/n1 + s2²/n2)
t  = (mean1 − mean2) / SE
```

В коде тест доступен, если в каждой группе хотя бы два валидных ответа. Значимость определяется приближённо как `|t| > 1,96`; точные степени свободы и t-распределение не рассчитываются.

Простыми словами: сравниваются средние двух групп с учётом того, насколько сильно различаются ответы внутри каждой группы. Одинаковая разница средних выглядит надёжнее на большой и однородной выборке, чем на маленькой группе с большим разбросом.

### 6.4. Доверительный интервал eNPS

Для eNPS рассчитывается 95%-ная погрешность:

```text
p = доля промоутеров
d = доля критиков
Var = (p + d) − (p − d)²
margin = 1,96 × √(Var/n) × 100
```

Результат читается как `eNPS ± margin`.

Изменение eNPS между годами считается реальным, если:

```text
|eNPS1 − eNPS2| > √(margin1² + margin2²)
```

Если условие не выполнено, обычный и расширенный отчёты подписывают разницу как находящуюся в пределах погрешности.

### 6.5. Что означает правило 5%

Граница `1,96` соответствует правилу приблизительно 95%-ной уверенности. Его проще понимать с обратной стороны:

> Если реального различия нет, один такой тест всё равно может показать ложный сигнал примерно в 5 случаях из 100.

Это **не означает**, что 5% сотрудников дали сомнительные ответы, что 5% данных ошибочны или что у вывода ровно 95% вероятности быть правильным. Речь только о допустимом риске случайной тревоги в одной статистической проверке.

Когда отчёт одновременно проверяет много вопросов и срезов, случайные сигналы накапливаются. Например, среди 20 независимых проверок без реальных изменений в среднем можно ожидать около одного ложного срабатывания. Проверки в этом отчёте не полностью независимы, поэтому пример нельзя использовать как точный прогноз, но он хорошо объясняет сам риск.

Поэтому пометка «значимо» означает **«сигнал достаточно надёжен, чтобы его изучить»**, а не «проблема доказана и решение уже понятно». Для управленческого вывода дополнительно нужны:

- достаточное `n`;
- практически заметный размер изменения;
- согласованность с другими показателями и комментариями;
- понятный рабочий контекст;
- по возможности повторение сигнала в следующем замере.

Текущий код не вводит формальную поправку на большое число одновременных проверок. Поэтому одиночную значимую находку безопаснее считать поводом для проверки, а несколько согласованных сигналов — более сильным основанием для вывода.

### 6.6. «Заметное» не равно «значимое»

В `ReportBuilder` есть отдельные UX-пороги для визуального отбора изменений:

| Вид изменения | Порог заметности |
|---|---:|
| Средняя rating5 | 0,30 балла |
| Доля в блоке «Заметные изменения» | 3 п.п. |
| Табличная подсветка дельт распределений и Top-5 | 5 п.п. |

Эти пороги не заменяют статистические тесты. Изменение может попасть в блок по величине, но иметь `significant = false`; тогда отчёт должен читать его как неподтверждённое выборочное колебание.

### 6.7. Разбор структуры eNPS

Short Summary пытается объяснить заметную дельту eNPS по структуре промоутеров, нейтралов и критиков. Правила применяются по порядку:

1. Если критики почти не изменились (`|Δ| ≤ 1`), а промоутеры и нейтралы заметно сдвинулись в разные стороны, выводится переток между ними.
2. Если изменение критиков больше изменения промоутеров, основным вкладом называются критики.
3. Если промоутеры и критики заметно движутся в противоположных математических направлениях, но в одну сторону для eNPS, они считаются взаимно усиливающими факторами.
4. Если сам eNPS изменился минимум на 3 пункта, но доминирующего фактора нет, выводится нейтральное описание структуры.

Это описательная эвристика. Она не доказывает причины изменения eNPS.

### 6.8. eNPS среза относительно компании

Если обычный отчёт построен с фильтрами, Short Summary дополнительно считает eNPS всей компании за тот же год без фильтров:

```text
разница с компанией = eNPS среза − eNPS всей компании
```

Срез подписывается как находящийся выше, ниже или на уровне компании. Если он ниже компании минимум на 20 пунктов, строка получает предупреждающий акцент. Для этого сравнения отдельный статистический тест не выполняется: порог 20 пунктов — визуально-управленческая эвристика.

## 7. Светофор расширенной аналитики

Для каждого шкального вопроса выбирается основной показатель:

| Тип | Показатель светофора |
|---|---|
| `rating5` | средний балл |
| обычный `scale4` | доля кодов 3–4, то есть позитив |
| Выгорание | доля кодов 1–2, то есть регулярный/постоянный риск |
| Смена работы | доля кодов 1–2, то есть мысли время от времени/постоянно |
| `eNPS` | eNPS в пунктах |

### 7.1. Пороги статуса

| Показатель | ОТЛИЧНО | ХОРОШО | ВНИМАНИЕ | КРИТИЧНО |
|---|---:|---:|---:|---:|
| rating5 | ≥ 4,50 | 4,30–4,49 | 4,10–4,29 | < 4,10 |
| scale4, позитив | ≥ 95% | 90–94,9% | 85–89,9% | < 85% |
| eNPS | ≥ 60 | 40–59 | 20–39 | < 20 |
| Выгорание, риск | ≤ 10% | >10–15% | >15–20% | > 20% |
| Смена работы, риск | ≤ 5% | >5–10% | >10–15% | > 15% |

В `Norms.THRESHOLDS` также определены границы охвата 70/50/35%, но текущий `AnalyticsService` не присваивает охвату отдельный статус светофора. Он выводит охват как дополнительную колонку.

Пороги — внутренние правила проекта, а не внешние отраслевые бенчмарки. Они были вручную закреплены в коде как рабочие зоны оценки; для `rating5` в комментариях к коду отдельно указано, что границы подстроены под наблюдаемый узкий диапазон высоких оценок. Формальный расчёт порогов по историческому распределению, внешнему рынку или связи с бизнес-результатами в проекте не зафиксирован.

Для менеджера это означает следующее:

- цвет — удобная навигация по отчёту, а не математический диагноз;
- переход через границу, например с 4,29 до 4,30, меняет цвет, но не превращает ситуацию мгновенно в принципиально другую;
- цвет отвечает на вопрос «в какой зоне находится уровень», а статистическая значимость — «насколько надёжно отличие или изменение»;
- до отдельной калибровки на исторических данных пороги следует считать рабочими и предварительными.

### 7.2. Уровень 0–100

Для сопоставления разных шкал средний код вопроса переводится на единую шкалу:

```text
уровень = (среднее − минимум шкалы) / (максимум − минимум) × 100
```

Пример: среднее `4,2` на шкале 1–5 даёт `(4,2 − 1) / 4 × 100 = 80`.

Уровень 0–100 — линейное преобразование исходного среднего, а не процент позитивных ответов и не вероятность. У eNPS-строки уровень строится по среднему исходному баллу рекомендации 0–10, тогда как статус строится по самому eNPS.

## 8. Корреляции и драйверы

### 8.1. Корреляция Спирмена

Для пары вопросов:

1. Остаются только респонденты, у которых есть оба ответа.
2. Значения каждого вопроса заменяются рангами.
3. Одинаковые значения получают средний ранг.
4. По двум рядам рангов считается корреляция Пирсона.

Если пар меньше 30, коэффициент не рассчитывается.

Ориентиры для чтения, зафиксированные в комментариях к коду:

| Модуль `r` | Интерпретация |
|---:|---|
| < 0,10 | практически нет связи |
| 0,10–0,25 | слабая связь |
| 0,25–0,40 | умеренная связь |
| > 0,40 | сильная для опросных данных |

Все основные шкалы направлены «больше = лучше», поэтому ожидаемые полезные связи положительные. В матрице приоритетов код сравнивает именно `r`, а не `|r|`.

Корреляция не доказывает причинность. Она показывает совместное изменение ответов, но не отвечает, что является причиной, а что следствием.

### 8.2. Матрица целей

Каждый шкальный вопрос сопоставляется с тремя целями:

- eNPS;
- выгоранием;
- сменой работы.

Это позволяет отличить факторы общей лояльности от факторов благополучия и удержания.

### 8.3. Матрица приоритетов

Для каждого вопроса рассчитываются:

- влияние — корреляция с eNPS;
- уровень — средний код, нормализованный к 0–100;
- база — число парных ответов;
- доля валидных ответов от всей выборки.

Границы матрицы вычисляются заново внутри текущей выборки:

- граница влияния — медиана ненулевых `r`;
- граница уровня — среднее всех уровней.

| Уровень | Влияние | Квадрант |
|---|---|---|
| ниже границы | не ниже медианы | ЧИНИТЬ ПЕРВЫМ |
| не ниже границы | не ниже медианы | ДЕРЖАТЬ |
| ниже границы | ниже медианы | СЛЕДИТЬ |
| не ниже границы | ниже медианы | ОК |

Если вопрос оказался в `СЛЕДИТЬ`, но его уровень ниже средней границы более чем на 8 пунктов, код добавляет примечание о ручном поднятии приоритета.

Если валидных ответов меньше 80% всей выборки и влияние высокое, ставится предупреждение о возможном эффекте отбора.

### 8.4. Разрыв промоутеры — критики

Для каждого вопроса отдельно считаются средние среди промоутеров и критиков:

```text
gap = среднее промоутеров − среднее критиков
```

Чем больше разрыв, тем сильнее ответы двух групп различаются по этому вопросу. Если критиков меньше 20, разрыв помечается как нестабильный.

## 9. Анализ срезов

### 9.1. Какие срезы строятся

Для любого доступного года:

- формат работы;
- стаж;
- город;
- отдел;
- управление;
- группа команд (пара «Управление + Тип команды», см. 3.5) — отдел без указанного типа команды в этот срез не попадает, но остаётся во всех остальных.

Только для 2026 дополнительно:

- соответствие ожиданиям;
- грейд;
- роль в отделе.

У трёх перформанс-срезов нет истории 2025, поэтому для них не рассчитываются годовая динамика и изменение состава.

### 9.2. Норма компании

Каждая группа сравнивается со всей текущей отфильтрованной выборкой. Норма — не внешний бенчмарк, а показатель компании в том же отчёте.

Основные метрики среза:

- eNPS;
- доля критиков;
- риск выгорания;
- риск ухода;
- средние по пяти вопросам: `ЗП`, `Удовлетворенность рабочими задачами`, `Возможности роста`, `Цели компании`, `ОС от руководителя`.

Отклонение фиксируется, если модуль разницы не меньше порога:

| Вид показателя | Порог |
|---|---:|
| Средний балл | 0,20 |
| Доля | 7 п.п. |
| eNPS | 15 пунктов |

Для eNPS хорошее направление — вверх; для критиков и рисков — вниз; для средних — вверх.

### 9.3. Малые группы и подтверждённые срезы

Все непустые группы показываются.

- `fragile = true`, если текущее `n < 25`;
- `previousFragile = true`, если прошлогоднее `n` от 1 до 24;
- `confirmed = true`, если у группы не меньше двух плохих отклонений.

`confirmed` — эвристическая защита от единичных случайных находок, а не статистическая поправка на множественные сравнения.

**`fragile` — это чувствительность метрики, а не репрезентативность.** Типичный отдел компании — 10-12 человек. `fragile` (`n < 25`) сам по себе говорит только о том, что один ответ заметно двигает показатель — он ничего не знает о том, какую долю отдела опрос охватил. Эти две вещи разделены:

- `fullCoverage = true`, если для среза `Отдел`/`Управление`/`Группа команд` известна численность и `n === headcount` (точное целое, не округлённый процент);
- `previousFullCoverage` — то же самое для прошлого года.

Если `fullCoverage`, малое `n` не понижает надёжность вывода: результат описывает всю команду на момент опроса, а не выборку из неё. Формулировка «сигнал, а не факт» к такому срезу не применяется, статус «недостаточно данных» из-за одного только `n < 25` не присваивается, а подтверждённое (`confirmed`) отклонение не понижается до предупреждения только по этой причине. Единая точка сборки текста — `Segments.coverageCaveat(segment, previous)`.

**Надёжность ТЕКУЩЕГО результата и надёжность СРАВНЕНИЯ годов — две разные проверки, а не одна.** Подтверждённое (`confirmed`) отклонение считается по данным ТЕКУЩЕГО года (см. 9.2), поэтому его серьёзность/статус должны зависеть только от текущего года — прошлогодняя явка или малая база к самому отклонению отношения не имеют. Смешивать их методически неверно: отдел с полным текущим охватом не должен получать статус «недостаточно данных» только потому, что в прошлом году явка была ниже.

- `Segments.currentReliabilityLimited(segment)` — только текущий год: `coverageCaveat(segment, false).limitsReliability` ИЛИ нет валидной текущей метрики (`metrics.enpsMargin === null`). Не включает `previousLowCoverage`/`previousFragile`/`previousHeadcountUnreliable`/`previousFullCoverage` и другие ограничения прошлого года.
- `Segments.yearComparisonLimited(segment)` — надёжность именно СРАВНЕНИЯ двух периодов: ограничена текущая база, ИЛИ ограничена прошлогодняя, ИЛИ одного из периодов нет. Используется только там, где отчёт говорит о динамике (yearDelta и подобные подписи), и не влияет на статус самого текущего результата.

`AnalyticsService.findings()` (п.6) и лист «Отклонения срезов» вычисляют severity/статус ТЕКУЩЕГО результата через `currentReliabilityLimited` — обе поверхности вызывают одну и ту же функцию, а не считают условие каждая по-своему, иначе один и тот же срез мог получить противоположные выводы на разных листах. `yearComparisonLimited` используется только для отдельной подписи рядом с годовой динамикой и не подменяет действующий расчёт `yearDelta.meaningful` (см. 9.4) — тот использует свой критерий (оба года `n ≥ FRAGILE_SEGMENT_SIZE`) и не меняется.

Для срезов, где явка не считается (город, стаж, формат работы и другие — см. 9.5), `headcount` всегда `null`, и `coverageCaveat` не может определить `fullCoverage` — там `fragile` по-прежнему читается как обычная числовая осторожность (малая база, широкий интервал), без утверждений о доле охваченного контура.

### 9.4. Динамика eNPS сегмента

Дельта считается, если группа существует в обоих годах. Она помечается `meaningful`, только если:

- обе группы имеют `n ≥ 25`;
- модуль дельты больше `(margin текущего года + margin прошлого года) / 2`.

Это отдельное эвристическое правило `Segments`; оно не совпадает с проверкой общей динамики eNPS через совместную погрешность `√(margin1² + margin2²)`.

### 9.5. Численность и явка

Лист `Численность` редактируется непосредственно в Google Sheets. Одна строка содержит год, стабильный ID отдела, управление этого года, название этого года и число приглашённых. Один ID связывает переименованный или перемещённый отдел между периодами. ID можно заполнить позже: до этого временной привязкой служит название отдела. Незаполненный или ошибочный справочник не блокирует расширенную аналитику — в ней просто не выводятся численность и явка.

Для 2025 и 2026 явка рассчитывается раздельно:

```text
явка года = число анкет года / число приглашённых в этом же году × 100%
```

- ниже 50% — `lowCoverage`;
- ровно 100% (по точным целым `n === headcount`, не по округлённому проценту) — `fullCoverage`: ответили все приглашённые, срез описывает всю команду;
- выше 100% — `headcountUnreliable`, то есть справочник устарел или не согласован с ответами.

Без фильтров знаменатель — вся численность года. При фильтрах только по отделу, управлению и/или группе команд знаменатель складывается из выбранных строк справочника за тот же год (`Headcount.invitedForFilters`) — все три фильтра пересекаются через **И**. Для группы команд в сумму входят только отделы, у которых за этот год явно указаны и управление, и тип команды: пустые типы в знаменатель не попадают. Для фильтров по городу, стажу, формату, оценкам и другим признакам явка не выводится: справочник не содержит числа приглашённых в этих подгруппах, поэтому корректного знаменателя нет.

Сквозная когорта также не получает явку: размер когорты — это только люди, сопоставленные между двумя годами, а не все заполнившие анкету.

### 9.6. Нормализация города

Крупные города из закрытого списка остаются отдельными группами. Остальные объединяются в `Прочие города`; ответы про удалённую работу, перемещения, `-`, `—` и `другое` объединяются в `Город не указан / удалённо`.

Это прикладная группировка текущего кода, а не географический классификатор.

### 9.7. Изменение состава выборки

Для каждого обычного среза сравнивается доля группы в выборке двух лет:

```text
shift = доля группы сейчас − доля группы раньше
```

Сдвиг считается материальным при `|shift| ≥ 3 п.п.`. Он предупреждает, что общая динамика может быть частично связана с другим составом респондентов, но сам по себе не доказывает такую причину.

### 9.8. Сервисные vs доменные

Лист `Сервисные vs доменные` (модуль `TeamTypeComparison.gs`) — прямое сравнение двух групп команд ВНУТРИ одного управления, а не сравнение каждой группы с нормой всей компании (как на листе «Отклонения срезов», см. 9.1). Сравниваются:

- `Сервисная команда`;
- `Доменная разработка`;

строго внутри `Управление разработки ПО`. Сервисные команды других управлений (например ИТ-управления) и отделы без указанного типа команды в это сравнение не входят никогда — принадлежность определяется тем же составным ключом «Управление + Тип команды», что и срез «Группа команд» (см. 3.5).

Для каждого report-вопроса анкеты (кроме текстовых и `single`) строится строка со значениями обеих групп за 2026 и 2025, годовой динамикой каждой группы отдельно и разрывом между группами за 2026 год — у каждого числа свой `n`. Метрика и тест значимости выбираются по тому же правилу, что и в светофоре (`AnalyticsService.trafficLight_`) и срезах (`Segments.analyze`) — модуль не вводит альтернативную математику:

| Тип показателя | Значение | Проверка значимости |
|---|---|---|
| `eNPS` | доверительный интервал (`MathStats.enpsConfidence`) | сравнение ДИ (`MathStats.enpsChangeIsReal`) |
| `rating5` | среднее | t-критерий Уэлча (`MathStats.welchTest`) |
| Риск-вопросы (выгорание, смена работы) | доля негатива | z-критерий двух долей (`MathStats.zTestProportions`) |
| Обычные `scale4`/`scale5` | доля позитива (два верхних деления) | z-критерий двух долей |

Отсутствие данных (нет ответов у группы за год) даёт `null`, а не 0 — пустое значение не превращается в фиктивный ноль ни в значении, ни в значимости (`gapSignificant`/`significant` тоже остаются `null`, что означает «сравнивать не с чем», а не «различий нет»). Комментарий к строке различает четыре исхода: статистически подтверждённое различие, описательную разницу без подтверждения, малую базу (`n < FRAGILE_SEGMENT_SIZE`) и отсутствие данных одного из годов — без причинных формулировок.

В отличие от обычного отчёта, сравнение не зависит от фильтров конкретного запуска Sidebar — как и лист «Руководитель и команда», оно всегда строится по всей компании (`AnalyticsWriter.prepareTeamTypeComparison_`).

## 10. Сквозная когорта

Когорта — люди, найденные и в 2025, и в 2026 после применения фильтров к каждому году отдельно.

### 10.1. Сопоставление

Ключ — `Фамилия Имя`. Перед сравнением:

- удаляются пробелы по краям;
- повторяющиеся пробелы схлопываются;
- регистр не учитывается;
- `ё` заменяется на `е`.

Пустые ФИО не участвуют. Если одно ФИО повторяется в данных прошлого года, ключ считается неоднозначным и полностью исключается. Если ключ повторяется в текущем году, в когорту попадает первая найденная строка, остальные пропускаются.

### 10.2. Парный t-критерий

Для одного вопроса берутся только пары, где у человека есть оба валидных ответа:

```text
di = ответ сейчас − ответ раньше
SE = sd(di) / √n
t = mean(di) / SE
```

Парный тест не рассчитывается при числе валидных пар меньше 10. Значимость — `|t| > 1,96`.

Простыми словами: здесь сравниваются не две случайные группы, а ответы **одних и тех же людей** в двух замерах. Для каждого человека сначала определяется личное изменение, а затем проверяется, движутся ли эти изменения достаточно согласованно в одну сторону.

Число `t` показывает, насколько среднее изменение больше обычного разброса личных изменений. Граница `1,96` использует то же приближённое правило 5%: даже при отсутствии реального изменения иногда может появиться случайный сигнал.

Для небольшого числа пар это упрощение оптимистично. Например, при 10 парах точная граница двустороннего t-критерия была бы около 2,26, а код всё равно использует 1,96. Поэтому результат на 10–29 парах нужно читать особенно осторожно: пометка «значимо» здесь ещё не делает вывод окончательным.

В расширенной аналитике список парных изменений вообще не строится, если общий размер когорты меньше 30. Если когорта не меньше 30, отдельный вопрос может войти в расчёт при 10 и более валидных парах.

### 10.3. eNPS когорты

Код показывает eNPS обоих лет и его арифметическую дельту. Поле `significant` для когорты берётся не из сравнения двух eNPS-интервалов, а из парного t-критерия по исходным оценкам рекомендации 0–10 у одних и тех же людей.

Поэтому следует различать:

- изменение eNPS как агрегированной доли;
- изменение среднего индивидуального балла рекомендации.

### 10.4. Отдельный когортный отчёт

В Sidebar можно построить обычный детальный отчёт только по когорте. Он доступен только для источника 2026 и всегда сравнивает с 2025. Все метрики обоих лет считаются по согласованным массивам одинакового размера.

ФИО участников выводятся только на самом когортном листе. Это персональные данные; доступ к такому листу должен быть ограничен.

Уровень показателя когорты нельзя автоматически переносить на всю компанию: подписанные анкеты могут систематически отличаться от анонимных. Основная ценность когорты — динамика у одних и тех же людей.

## 11. Обогащение данными «перформанс»

Справочник `перформанс` используется только для 2026. Обязательные колонки:

- `Фамилия Имя`;
- `Город`;
- `Отдел`;
- `Соответствие ожиданиям`;
- `Грейд`;
- `Руководитель отдела`.

К ответам в памяти добавляются:

- `Соответствие ожиданиям`;
- `Грейд`;
- `Роль в отделе`.

Эти поля не кодируются как показатели, не попадают в светофор и не участвуют в корреляциях. Они используются только как фильтры и отдельные срезы.

Сопоставление идёт по ФИО без учёта регистра и повторяющихся пробелов. После совпадения ФИО дополнительно проверяются город и отдел. Если они расходятся, все три присоединяемых поля остаются пустыми.

Обычный отчёт работает по мягкому сценарию: если лист `перформанс` отсутствует или структурно сломан, опрос 2026 загружается без обогащения. Отчёт `Руководитель и команда` использует строгий сценарий и требует корректного справочника.

Перформанс-фильтры и срезы доступны только для 2026. Сравнение с 2025 и когортный режим блокируются, если применён фильтр `Соответствие ожиданиям`, `Грейд` или `Роль в отделе`.

## 12. Сравнение «Руководитель и команда»

### 12.1. Состав команды

Отчёт строится только по ответам 2026.

- Отдел берётся из ответа респондента.
- Руководитель определяется чекбоксом в справочнике `перформанс`.
- Команда — все ответившие из отдела, кроме строки найденного руководителя.
- Наличие каждого сотрудника команды в справочнике `перформанс` не требуется.

Отдел без отмеченного руководителя пропускается. Отдел с несколькими отмеченными руководителями выводится как ошибка без расчёта.

### 12.2. Расчёт

Для каждого шкального вопроса:

1. Ответ руководителя кодируется через `Scoring`.
2. Среднее команды считается по валидным ответам сотрудников.
3. Оба значения переводятся на шкалу 0–100.
4. Рассчитывается разница:

```text
diff = уровень руководителя − уровень команды
```

Положительная разница означает, что руководитель оценивает тему выше команды; отрицательная — команда выше руководителя.

Ответы руководителя `не пользовался`, `затрудняюсь ответить`, пустая ячейка и нераспознанный текст получают разные статусы, но числовую разницу не формируют.

### 12.3. Надёжность по размеру команды

`n` считается отдельно по каждому вопросу.

| n команды | Статус |
|---:|---|
| 0 | нет ответов команды |
| 1–2 | очень мало данных |
| 3–4 | мало данных |
| ≥ 5 | достаточно данных |

Среднее показывается при любом `n ≥ 1`, но автоматическая интерпретация выполняется только при `n ≥ 5` и валидном ответе руководителя.

При `n = 1` среднее фактически раскрывает ответ одного сотрудника. Лист следует защищать как персональные данные, даже если ФИО на нём не показано.

### 12.4. Интерпретация разницы

Правила применяются строго по порядку:

1. `|diff| ≤ 10` — восприятие совпадает.
2. Уровень команды ниже 60 и `diff > 20` — возможная слепая зона руководителя.
3. Оба уровня ниже 60 и `diff < 20` — общая зона внимания.
4. `diff < −20` — руководитель оценивает ситуацию критичнее команды.
5. Остальные случаи — умеренное расхождение.

Если данных недостаточно, содержательная интерпретация не выполняется.

Поле `significantCount` в этом отчёте не означает статистическую значимость. Оно считает темы со статусом «достаточно данных», попавшие в категории «слепая зона» или «руководитель критичнее».

Общий статус отдела:

- `Оценки близки` — есть сравнимые темы и `significantCount = 0`;
- `Есть расхождения` — есть сравнимые темы и `significantCount > 0`;
- `Недостаточно данных для сравнения` — нет ни одной темы с полностью надёжным сравнением.

Темы сортируются по убыванию `|diff|`, а отделы — по убыванию числа таких расхождений.

## 13. Сводная аналитика и heatmap

`Сводная аналитика` — долгоживущий лист: одна строка соответствует одной построенной выборке. Он не пересчитывает статистику, а переносит готовые значения из того же `reportData`, из которого создан детальный отчёт.

Скрытый первый столбец хранит технический JSON-ключ строки: источник, нормализованные фильтры и признак когорты, если он включён. Флаг «Сравнить с 2025» в этот ключ не входит, поэтому повторная сборка той же выборки с другим состоянием флага обновляет ту же строку. Независимо от флага сравнения сводная пытается заполнить eNPS и размер выборки за оба доступных года.

Для вопросов «Да / Скорее да / Скорее нет / Нет» `Heatmap` сравнивает долю позитивных ответов между всеми строками сводной.

Алгоритм:

1. Строки с базой меньше 5 исключаются из раскраски.
2. Если размах между лучшей и худшей выборкой меньше 5 п.п., заливки нет.
3. Для остальных считается положение между максимумом и минимумом.
4. Лучшая треть остаётся без заливки, средняя треть получает жёлтую, нижняя — красную.

Это относительная heatmap между строками сводной, а не сравнение с порогами `Norms` и не проверка статистической значимости.

## 14. Автоматические наблюдения

`AnalyticsService.findings()` формирует не AI-выводы, а сообщения по фиксированным правилам.

Правила текущей реализации:

1. Если дельта eNPS есть, но не выходит за совместную погрешность, выводится «динамики eNPS нет».
2. Для значимых изменений остальных вопросов формируется сообщение о росте или снижении.
3. Значимые парные изменения когорты выносятся отдельно.
4. Вопросы со статусом `КРИТИЧНО` попадают в выводы.
5. Если `r с eNPS ≥ 0,30`, а охват упал минимум на 3 п.п., формируется предупреждение о сужении охвата сильного драйвера.
6. По каждому измерению берутся до пяти срезов с `confirmed = true`.
7. Материальные изменения состава (`≥ 3 п.п.`) выводятся как контекст.
8. Группа `затрудняюсь ответить` попадает в наблюдения, если её доля не меньше 5% и её eNPS или доля критиков заметно хуже нормы компании.

Сначала сортируются критичные сообщения, затем предупреждения, затем справочные.

Есть важная особенность фактического кода: в правиле 2 знак дельты трактуется буквально. Для обратных риск-метрик снижение риска математически отрицательно, но текстовый генератор может назвать его «снижением» и присвоить предупреждающий уровень. Поэтому автоматические сообщения по выгоранию и уходу нужно сверять с направлением метрики вручную.

## 15. Основные ограничения методики

1. **Корреляция не равна причинности.** Драйвер — статистическая связь, а не доказанная причина.
2. **Пороги внутренние.** Светофор и отклонения настроены в коде проекта и не являются отраслевыми нормами.
3. **Тесты приближённые.** Для Уэлча и парного теста используется фиксированная граница 1,96 без расчёта точных степеней свободы.
4. **Нет формальной поправки на множественные сравнения.** В срезах вместо неё используется правило «не меньше двух плохих отклонений».
5. **Малые группы показываются, но нестабильны.** Метка `fragile` не исправляет широкую погрешность, а только предупреждает о ней. Для срезов «Отдел»/«Управление»/«Группа команд» с `fullCoverage` (ответили все) это предупреждение — про чувствительность метрики к отдельным ответам, а не про недостаток данных: сам вывод при этом не понижается до «сигнал, а не факт» или «недостаточно данных» (см. 9.3).
6. **Когорта зависит от ФИО.** Опечатки, смена фамилии и неоднозначные дубли уменьшают сопоставление.
7. **Перформанс есть только за 2026.** Его нельзя корректно использовать для годового сравнения.
8. **Явка доступна не для любого фильтра.** Точный знаменатель есть для компании, отдела и управления; для города, стажа и ответов на вопросы нужна отдельная численность приглашённых по этим признакам.
9. **Город группируется эвристически.** Свободный текст не заменяет устойчивый справочник городов.
10. **Темы комментариев словарные.** Они требуют чтения исходных комментариев перед управленческим выводом.
11. **Расширенная аналитика всегда рассчитывается по всей компании.** Фильтры, выбранные для обычного отчёта, на неё не влияют. Поэтому листы `Выводы`, `Светофор`, `Драйверы` и `Когорта` нельзя воспринимать как аналитику только по выбранному отделу, городу или другой группе. Отдельные группы следует смотреть на листе `Отклонения срезов`.
12. **Пустая ячейка в числовом фильтре — известный риск.** `FilterEngine.matchesOperator()` напрямую применяет `Number(rawValue)`, поэтому пустое значение превращается в 0 и может ошибочно пройти фильтр eNPS вроде `<= 6` или `= 0`. В самих расчётах eNPS эта ошибка устранена через `Scoring.vector()`, но в числовой фильтрации — нет.

## 16. Где настраивается методика

| Что меняется | Файл / константа |
|---|---|
| Карта вопросов и варианты ответа | `Questions.catalogue` |
| Кодирование шкал и категории eNPS | `Scoring.MAPS`, `Scoring.ENPS_THRESHOLDS` |
| Пороги светофора | `Norms.THRESHOLDS` |
| Пороги отклонений срезов | `Norms.DEVIATION` |
| Граница малой группы | `Norms.FRAGILE_SEGMENT_SIZE` |
| Граница низкой явки | `Norms.LOW_COVERAGE_THRESHOLD_PERCENT` |
| Текст про полный охват/чувствительность малого n | `Segments.coverageCaveat()` |
| Надёжность текущего результата (не зависит от прошлого года) | `Segments.currentReliabilityLimited()` |
| Надёжность сравнения с прошлым годом | `Segments.yearComparisonLimited()` |
| Знаменатель риск-метрик | `Norms.RISK_DENOMINATOR` |
| Риск эффекта отбора драйвера | `Drivers.SELECTION_BIAS_COVERAGE` |
| Материальный сдвиг состава | `Segments.compositionShift()` — 3 п.п. |
| Пороги заметных изменений обычного отчёта | `ReportBuilder.DELTA_THRESHOLD_*`, `DRAMATIC_CHANGE_THRESHOLD_PERCENT_` |
| Порог охвата для Top/Bottom средних | `ReportBuilder.MIN_COVERAGE_PERCENT_` |
| Словарь тем комментариев | `ReportBuilder.THEME_DICTIONARY_` |
| Размеры команды и интерпретация разницы | `ManagerTeamReport.MIN_TEAM_SIZE`, `INTERPRETATION_THRESHOLDS` |
| Численность, управления, тип команды и годовые названия | лист `Численность` |
| Связь переименованного отдела между годами | одинаковый `ID отдела` на листе `Численность`; `DepartmentAliases.REGISTRY_` — резерв для известных старых названий |
| Составной ключ группы команд («Управление + Тип команды») | `Headcount.TEAM_GROUP_SEPARATOR`, `Headcount.teamGroupOf()` |
| Управления и группы для сравнения «Сервисные vs доменные» | `TeamTypeComparison.TARGET_DIVISION`, `GROUP_A_LABEL`, `GROUP_B_LABEL` |

После изменения порогов нужно проверять одновременно обычный отчёт, расширенную аналитику и сводную: часть пользовательских подписей и визуальных правил находится в `ReportBuilder`, а часть — в `Norms` и `AnalyticsService`.
